API Automation

PARTIAL PROOF

Relier deux services ou supprimer une tâche répétitive via API, webhook ou script.

Tool-first route

  1. 01Lire le contrat API / OpenAPI et identifier l'authentification.
  2. 02Prouver le flux avec curl avant d'écrire du code.
  3. 03Utiliser Node.js fetch ou la bibliothèque standard Python pour le plus petit script possible.
  4. 04Ajouter timeouts, erreurs explicites et configuration par variables d'environnement.
  5. 05Capturer une exécution de test reproductible sans secrets.

Outils primaires

  • • curl
  • • OpenAPI/Swagger quand disponible
  • • Node.js fetch
  • • GitHub

Fallback

  • • Python standard library
  • • Docker pour isoler l'exécution

Livrables

  • • script ou petit adaptateur API
  • • .env.example
  • • README d'installation
  • • test/smoke check
  • • preuve d'exécution

Acceptance gate

  • • aucun secret commité
  • • flux nominal reproductible
  • • erreurs réseau gérées
  • • entrées/sorties documentées

Preuves publiques

KIF provider/fallback evidenceP01 support adapter

Limites

  • • Une intégration client spécifique n'est revendiquée qu'après test sur son API réelle.

CI/CD GitHub Actions

PUBLIC PROOF

Exécuter automatiquement lint, tests et build à chaque changement important.

Tool-first route

  1. 01Réutiliser les scripts locaux existants comme contrat de CI.
  2. 02Créer le workflow GitHub Actions minimal.
  3. 03Utiliser un runner standard et éviter les services externes inutiles.
  4. 04Faire échouer le workflow si lint, test ou build échoue.
  5. 05Publier le run comme preuve.

Outils primaires

  • • GitHub Actions
  • • npm scripts
  • • pytest / node:test selon le projet

Fallback

  • • runner auto-hébergé si une dépendance locale l'exige

Livrables

  • • workflow YAML
  • • pipeline lint/test/build
  • • badge optionnel
  • • run de preuve

Acceptance gate

  • • workflow vert sur la branche cible
  • • échec correct sur test invalide
  • • aucun secret exposé

Preuves publiques

P01 CI workflowsSkill 001 CI proof

Dockerisation

PARTIAL PROOF

Rendre une application plus reproductible avec une image et un démarrage documenté.

Tool-first route

  1. 01Identifier d'abord le runtime et la commande locale qui fonctionnent.
  2. 02Écrire le Dockerfile minimal.
  3. 03Ajouter Compose uniquement si plusieurs services sont réellement nécessaires.
  4. 04Tester build, start, health check et arrêt propre.
  5. 05Documenter volumes, ports et variables d'environnement.

Outils primaires

  • • Docker
  • • Docker Compose

Fallback

  • • GitHub Actions pour valider le build

Livrables

  • • Dockerfile
  • • compose.yaml si nécessaire
  • • .dockerignore
  • • .env.example
  • • instructions run/stop

Acceptance gate

  • • image construite
  • • conteneur démarre
  • • port/health check vérifié
  • • aucun secret intégré à l'image

Preuves publiques

Portfolio public evidence hub

  • • Une preuve Docker publique dédiée reste à publier dans P01.

Backend Prototype

PARTIAL PROOF

Livrer une petite API HTTP avec contrat clair, validation et procédure de test.

Tool-first route

  1. 01Définir d'abord les endpoints et exemples de requêtes/réponses.
  2. 02Choisir FastAPI quand OpenAPI interactif apporte de la valeur.
  3. 03Utiliser Node.js quand il réduit les dépendances dans un projet JavaScript existant.
  4. 04Tester les endpoints avant toute infrastructure supplémentaire.
  5. 05Dockeriser seulement si cela améliore réellement la livraison.

Outils primaires

  • • FastAPI + OpenAPI
  • • Node.js

Fallback

  • • Docker
  • • curl pour smoke tests

Livrables

  • • API minimale
  • • endpoints documentés
  • • validation d'entrée
  • • smoke tests
  • • README

Acceptance gate

  • • endpoints répondent comme documenté
  • • erreurs 4xx/5xx contrôlées
  • • configuration externe
  • • test reproductible

Preuves publiques

P01 support API adaptereCDF technical repository

Limites

  • • P01 ne revendique pas encore un backend client déployé en production.

Technical Audit

PUBLIC PROOF

Trouver rapidement les problèmes d'installation, structure, tests, CI, dépendances et documentation.

Tool-first route

  1. 01Lire README, package manifest et workflows avant toute modification.
  2. 02Exécuter les vérifications natives du projet.
  3. 03Inspecter git diff, historique pertinent et état CI avec git/gh.
  4. 04Classer les constats par bloquant, risque et amélioration.
  5. 05Proposer des correctifs reproductibles et vérifiables.

Outils primaires

  • • git
  • • gh CLI
  • • ESLint
  • • npm audit / tests natifs

Fallback

  • • scripts de secret scan
  • • Docker pour reproduire un environnement

Livrables

  • • rapport d'audit
  • • liste priorisée
  • • correctifs optionnels
  • • commandes de reproduction
  • • preuves avant/après

Acceptance gate

  • • chaque constat cite un fichier/commande
  • • séparation faits / recommandations
  • • aucun faux positif présenté comme certitude

Technical Documentation

PUBLIC PROOF

Rendre un projet compréhensible, installable et transmissible sans dépendre de son auteur.

Tool-first route

  1. 01Extraire les faits depuis le code, les scripts et la CI.
  2. 02Documenter installation, exécution, architecture et limites.
  3. 03Utiliser Markdown comme format canonique portable.
  4. 04Ajouter Mermaid uniquement quand un diagramme clarifie réellement le système.
  5. 05Vérifier chaque commande documentée.

  • • Markdown
  • • Mermaid
  • • GitHub

Fallback

  • • GitHub Pages / documentation statique

Livrables

  • • README
  • • SETUP.md
  • • architecture
  • • runbook
  • • limitations et preuves

Acceptance gate

  • • commandes testables
  • • architecture cohérente avec le code
  • • limitations explicites
  • • liens valides
